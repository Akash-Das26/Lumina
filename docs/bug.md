### BUG-014 — A placeholder provider key started the app, and the provider's own error text (with part of the key) was shown to the user
- **Severity / Status:** High / **Fixed** (2026-10-16, Session 23).
- **Where:** `artifacts/api-server/src/lib/provider-config.ts` (new), `artifacts/api-server/src/lib/provider-errors.ts` (new), `artifacts/api-server/src/lib/safe-error.ts` (key redaction), `artifacts/api-server/src/index.ts` (startup check + deferred router import), `artifacts/api-server/src/routes/openai/index.ts` (chat/image/search failure paths + retry dedupe), `artifacts/lumina/src/lib/stream-message.ts` (`ChatSendError`), `artifacts/lumina/src/pages/chat-conversation.tsx` (failed-send state, Retry, composer restore), `artifacts/lumina/src/components/{chat-input,message-bubble}.tsx`, `.env.example`, `README.md`, `scripts/browser/{stub-provider,verify-flow}.mjs`.
- **Symptom:** sending any chat message showed a red toast — `Message failed. 401 Incorrect API key provided: replace-*********-key. You can find your API key at https://platform.openai.com/account/api-keys`. The user's `.env` still held `.env.example`'s `OPENAI_API_KEY=replace-with-your-key`, so the provider rejected every request, and the client displayed the provider's raw message (an internal configuration detail, plus a fragment of the key itself).
- **Confirmed root cause (two separate defects, reproduced and traced):**
  - **Config was never validated.** The provider clients only checked that the variables were *present* (`if (!apiKey) throw`), so the documented placeholder passed as a configured key and the server started normally. The failure only appeared on the first request that spent a provider call.
  - **Provider errors were forwarded verbatim.** The chat route answered `res.status(502).json({ error: error.message })` (and the image route the same), so `streamMessage` → the page's toast rendered whatever the provider said. The pre-fix behaviour is pinned by the old `bug-002.spec.ts` assertion (`{ error: "connection refused" }`) and by `image.spec.ts` (`{ error: "image provider down" }`) — the provider's text was the API's response body.
  - Both problems also meant the *wrong* status: the caller's request was fine, the server's provider setup was not.
- **Fix applied:**
  - **Fail fast on bad provider config (before the first request):** `readProviderConfig()` treats an empty value and the documented placeholder shapes — `replace…` (including `.env.example`'s `replace-with-your-key` and `replace-with-a-random-32-plus-character-secret`), `your-api-key`, `changeme`, `xxx`, `<your-key>`, `placeholder`, `todo` — as *not configured*, and also rejects a missing or malformed `AI_INTEGRATIONS_OPENAI_BASE_URL` (a scheme-less value used to crash the SDK with `Invalid URL`). `index.ts` runs the check first and exits 1 with a synchronous stderr line that names the variable, points at `.env` / `.env.example` / `README → Run locally`, and **never prints the value**. Because importing the router constructs the provider SDK (which refuses to build without credentials, `Missing credentials…`), the app module is now imported *after* the checks (`await import("./app")`), so the setup message is always the one that wins. Measured: placeholder key, empty key, placeholder alias, bad base URL → exit 1 with the named-variable message and no value in the output; valid config + unreachable database → the database message, confirming the order.
  - **Map provider failures to safe client copy:** new `lib/provider-errors.ts` classifies every failure — provider 401/403 → **502** "The AI service is not configured correctly. Please contact the administrator.", 429 → **503** "The AI service is busy or over quota. Please try again later.", timeouts and connection failures (incl. provider 408/504) → **504** "The AI service did not respond. Please try again.", anything else (including a provider-side 5xx) → generic **500**. It looks through `cause` chains, falls back to logging the provider's *own* message (redacted), and is used by the chat route (JSON **and** the mid-stream SSE frame), the image route and the Search failure path — so no route can forward provider text or an unmapped status again.
  - **Log the real cause, redacted:** `logProviderError` writes one `error`-level record per failure with `reqId`, route, mode, provider status and code, the redacted provider message, and the stack. `lib/safe-error.ts` now strips more than URLs: configured secret values (`OPENAI_API_KEY`, `AI_INTEGRATIONS_OPENAI_API_KEY`, `SESSION_SECRET`, ≥8 chars), `sk-`/`gsk_`/`xai-`-shaped keys, and the provider's masked echo (`replace-*********-key`).
  - **Frontend:** `streamMessage` throws a `ChatSendError` carrying the API's mapped `error` copy and the HTTP status; the page shows that copy in the toast (titles unchanged per tool), keeps the failed user message in place with an inline **Message failed to send** + **Retry** control (`components/message-bubble.tsx`), and drops the assistant placeholder. When there was *no HTTP response at all*, nothing was persisted anywhere: the optimistic bubble is dropped and `ChatInput` puts the typed text back in the composer (`onSend` resolving `true`), so a network failure cannot cost the user their message. Retry resends the same content with the mode it was sent with.
  - **Retry does not duplicate the prompt:** the messages route loads history *before* persisting, and when the last persisted message is an unanswered user message with the same content it reuses it instead of inserting a second copy — otherwise a Retry (the previous attempt already saved the prompt) would duplicate it in the transcript and in every later provider call.
  - **Docs:** `.env.example` documents which features need the key, where to get one, the restart requirement and what each mapped message means; README gained a symptom → status → cause → fix table for the four messages plus the startup-refusal cases.
- **Test added:** `api-server/test/provider-config.spec.ts` (41: empty/whitespace/missing, 15 placeholder shapes, alias precedence, a real-looking and a `gsk_` key, the suite's own `test-key`/`stub-key`, missing/malformed base URL, and an assertion that the offending value — unique tail included — never appears in the message); `api-server/test/provider-errors.spec.ts` (9: 401/403→502, 429→503, timeouts/connection failures→504, unclassified→500, wrapped `cause` chains, no provider text in any client message, a logger spy proving the log carries status/code/request id and no key material, and `redactSecrets` cases for real keys, configured secrets and the masked echo); `api-server/test/bug-014.spec.ts` (11: chat 401/429/timeout/other → 502/503/504/500 with no provider text in the body but the real details in the log; the mid-stream SSE frame carries mapped copy; image 401 → 502 with the same copy; **chat still works after the image provider fails**; the Search failure path maps to 504 and a two-source outage still degrades to an empty list; retry reuses the unanswered prompt while a genuinely new message is still inserted); lumina `test/chat-send-failure.spec.tsx` (4: failed state + mapped toast with no provider text in the DOM or toast, Retry resending and clearing the failed state, a failed Search source lookup using the API's copy, and the typed text restored on a no-response failure) plus `chat-input.spec.tsx` +2 and `message-bubble.spec.tsx` +3. `bug-002.spec.ts` and `image.spec.ts` expectations were updated to the mapped statuses (connection failure 504; unclassified 500) — intentional behaviour changes, not test weakening.
- **Verified by:** whole-workspace `pnpm test` exit 0 — **293 passed + 4 env-gated skipped** (6 api-client-react + 155 api-server + 132 lumina), up from 223 + 4 (api-server 94 → 155, lumina 123 → 132); `pnpm typecheck` exit 0. Real browser (throwaway PostgreSQL + real API + Vite + headless Chrome over CDP, `pnpm verify:flow`, extended with a provider-failure step): the stub provider rejects the key with the real `401 Incorrect API key provided: replace-*********-key…` message, both chat sends are answered **502**, the page shows the mapped administrator copy, the message is marked `Message failed to send` with a working Retry that resends (second 502), and no provider text, URL or key fragment appears anywhere in the page; zero page exceptions. Startup refusals were measured directly against the built server (exit 1, variable named, no value echoed). No new dependencies.
- **Limitations:** the reproduction used an OpenAI-compatible stub returning the provider's 401 (never the real endpoint, so no request with the placeholder key left the machine); the frontend cannot sanitise arbitrary provider text, so the guarantee lives in the API contract (asserted) — the client only ever displays the mapped copy; a provider failure *after* streaming has begun is still delivered in-band, now with mapped copy.

### BUG-013 — Valid registration showed a generic banner; the real cause was an unreachable database hidden by an HTML 500
- **Severity / Status:** High / **Fixed** (2026-10-16, Session 22).
- **Where:** `artifacts/api-server/src/app.ts` (no error-handling middleware), new `artifacts/api-server/src/middleware/error-handler.ts`, new `artifacts/api-server/src/lib/safe-error.ts`, new `artifacts/api-server/src/lib/database.ts`, `artifacts/api-server/src/index.ts` (startup check), `artifacts/api-server/src/routes/{auth,health}.ts`, `lib/db/src/index.ts` (pool `error` listener), `artifacts/lumina/src/lib/form-errors.ts`, `artifacts/lumina/src/pages/{sign-up,sign-in}.tsx`, `artifacts/lumina/vite.config.ts` (dev-proxy error response), `lib/api-spec/openapi.yaml` + regenerated clients.
- **Symptom:** submitting valid input (name "Akash", email `24155155@kiit.ac.in`, 10-character password) showed "Unable to create your account. Please try again." Client-side validation passed, so the failure was server-side — and the banner said nothing about it.
- **Confirmed root cause (reproduced, not guessed):** the developer machine's PostgreSQL is running, but the `DATABASE_URL` in `.env` cannot authenticate — `psql`-level error **`password authentication failed for user "lumina_user"`**. Every request that touches the database therefore fails. `POST /api/auth/register` answered **`500 text/html`** and the body was Express's default error page with the *entire stack trace* (`<pre>Error: Failed query: select "id", "email", "name", "password_hash" from "users" …`), so the JSON client found no `error` field and fell back to the generic banner. The API log contained only that raw stack line: no request id, no structured record, and **not the actual cause** (the authentication failure), which left a debugging session with no starting point. `GET /api/healthz` answered `200 {"status":"ok"}` the whole time because it never touched the database, so "is my setup fine?" could not be answered either.
- **Fix applied:**
  - **Environment (the actual cause) documented, not hacked around:** README gained a **Troubleshooting local setup** section that maps each symptom to its cause and fix — `database: unreachable` vs `schema-missing`, `password authentication failed for user …` (check the role/password behind `DATABASE_URL`, `ALTER ROLE … PASSWORD`, then re-run `pnpm db:push`), `database "lumina" does not exist`, `relation "users" does not exist`, and what an intentional startup exit means. `.env.example` now also documents `LOG_LEVEL`, `PGCONNECT_TIMEOUT`, `AI_INTEGRATIONS_OPENAI_API_KEY` (optional) and every other variable the code reads.
  - **Fail fast at startup:** `src/index.ts` probes the database before `app.listen` and exits `1` with a synchronous stderr line naming the reason and the fix (`Cannot reach the database…` / `The database is reachable but its schema is missing. Run `pnpm db:push``), including the redacted driver error. `scripts/dev-local.mjs` labels which service exited and points at the README. The provider variables already failed fast with a message naming the variable (now also pointing at `.env`).
  - **Readiness endpoint:** `GET /api/health` (documented in the OpenAPI spec, clients regenerated) answers `200 {status:"ok",database:"ok"}` or `503 {status:"degraded",database:"unreachable"|"schema-missing",message}`; `/api/healthz` stays a liveness probe with no database access.
  - **Real JSON error contract:** new `middleware/error-handler.ts` logs every 500 with the request id and the real error (message + stack + wrapping cause) through pino, and answers `{"error":"Internal server error"}` — never the stack, SQL, column names or connection details; body-parser failures become JSON `400 {"error":"Malformed request body."}` / `413`, and unmatched `/api` paths answer JSON instead of Express's HTML page. `lib/safe-error.ts` redacts anything URL-shaped, so no log or response can contain credentials (asserted in tests).
  - **Status codes:** `400` validation (with `fieldErrors`), `409 An account with this email already exists` — now including the concurrent-registration race, where PostgreSQL's `23505` on the unique email index used to become a 500 — and `500` generic.
  - **The API no longer dies with the database:** a dropped backend connection emits `'error'` on the pg pool; with no listener Node killed the whole process (reproduced: stopping PostgreSQL took the API down and later requests failed at the socket). `lib/db` now installs a listener (routed through the API's pino logger via `setPoolErrorHandler`) and the next query reconnects.
  - **Frontend messages:** the auth forms map failures to specific copy — `409` → "An account with this email already exists. Try signing in.", no response / `502`/`503`/`504` → "Can't reach the server. Check your connection and try again.", everything else keeps the generic message. The Vite dev proxy now answers a JSON `503` when the API process is down (instead of an opaque error page) so a stopped API is classifiable in dev too.

The 4 env-gated integration tests were also run for real against a throwaway PostgreSQL 18.6 (`schema pushed` via `db:push --force`, then `E2E_DATABASE_URL=… pnpm --filter @workspace/api-server test`) → **18 files / 98 passed / 0 skipped**, so the suite is 227 passed / 0 skipped with a live database and the new pool listener and readiness probe both behave against real SQL. ### BUG-012 — Raw Zod issues array rendered as text in the sign-up/sign-in forms
- **Severity / Status:** Medium / **Fixed** (2026-10-16, Session 21).
- **Where:** `artifacts/api-server/src/routes/auth.ts` (register + login) and `artifacts/api-server/src/routes/openai/index.ts` (9 schema checks) returned `parsed.error.message`; `artifacts/lumina/src/pages/sign-up.tsx` and `sign-in.tsx` rendered whatever string the API sent in a single banner; new `artifacts/api-server/src/lib/validation.ts`, `artifacts/lumina/src/lib/form-errors.ts`, `artifacts/lumina/src/lib/auth-schemas.ts`, `artifacts/lumina/src/components/field-error.tsx`.
- **Symptom:** submitting the Create Account form with an invalid email and a 6-character password printed the whole Zod issues array into the page — `[{"origin":"string","code":"invalid_format","format":"email","pattern":"/^(?!\\.)...","path":["email"],"message":"Invalid email address"},{"origin":"string","code":"too_small","minimum":8,"path":["password"],...}]` — regex patterns, error codes and JSON included.
- **Root cause:** in Zod **v4.5.2** (the installed version — confirmed via `node_modules/.pnpm/zod@4.5.2`) `ZodError.message` is `JSON.stringify(issues)`, not a human sentence. The routes answered `res.status(400).json({ error: parsed.error.message })`, so the serialised issues travelled as a normal API error string; the pages only had one error slot (`setError(err.data.error)`) and rendered it verbatim in the banner. Reproduced directly: `z.string().email().safeParse('bbjhbvb@ewfw').error.message` returns the JSON array (see the `invalid_format` pattern in the report). Validation ran on the server only — no client-side pre-submit check — and the sign-up inputs also carried native `required`/`type=email`, so mirroring the same bad pattern in the login form was invisible until the API answered.
- **Fix applied:**
  - **Server shape:** new `lib/validation.ts` with `formatZodErrors` (Zod v4 `z.flattenError`, which keys issues by `path[0]`) and `sendValidationError(res, error)` → `400 { error: "Validation failed", fieldErrors: { email: ["..."] }, formErrors: [] }`. All 11 `parsed.error.message` sites (auth register/login + the 9 openai schema checks) now use it, so no route can leak the issues array again.
  - **Client mapping:** new `lib/form-errors.ts` — one shared helper set used by every form: `formatZodErrors` (ZodError → one message per field), `formatApiFieldErrors` (reads the server's `fieldErrors`), `formatFormErrorMessage` (banner copy; falls back for missing, status-only `"Validation failed"` and raw-JSON-looking strings), `withoutFieldError` (clear on edit).
  - **Friendly schema messages:** new `lib/auth-schemas.ts` (+ the mirrored server schemas) — name "Please enter your name", email "Please enter a valid email address (e.g. name@example.com)" (trimmed, lower-cased, max 254), password "Password must be at least 8 characters" (max 128). `z.string({ error })` also replaces Zod's "Invalid input: expected string, received undefined" jargon; no new password rules were invented.
  - **Inline per-field display:** every input renders its message in a red `FieldError` directly underneath, wired with `aria-invalid`, `aria-describedby` → `<field>-error`, `role="alert"`, and an `aria-invalid:` destructive border on the shared `ui/input.tsx`. `noValidate` on both forms stops native bubbles from pre-empting the inline messages.
  - **Client validation + separation of concerns:** both forms validate with the shared schema before any request (and on blur, one field at a time); the server still re-validates. ### BUG-008 — GET conversation returned every message; images persisted as base64 data URIs
- **Severity / Status:** Medium / Fixed (2026-10-05, Session 20) — Audit 3 finding F-03; user-approved "Full fix" option.
- **Where:** artifacts/api-server/src/routes/openai/index.ts (GET conversation; generate-image; new GET images); lib/db/src/schema/message-images.ts (new table); lib/api-spec/openapi.yaml; artifacts/lumina/src/{lib/markdown.tsx, components/message-bubble.tsx, pages/chat-conversation.tsx}.

### BUG-007 — Rate limiters keyed on proxy IP; no `trust proxy` handling
- **Severity / Status:** Medium / Fixed (2026-10-05, Session 20) — Audit 3 finding F-02; user-approved "env-tunable" option.
- **Where:** artifacts/api-server/src/app.ts (limiter mounting + `trust proxy`); artifacts/api-server/src/middleware/rate-limit.ts (key generator); artifacts/api-server/src/routes/openai/index.ts (limiter mount point); .env.example (`TRUST_PROXY_HOPS`).
- **Symptom:** behind the Vite dev proxy or any reverse proxy, `req.ip` was the proxy address, so every client shared one bucket for chatLimiter (30/min), authLimiter (10/15 min) and registerLimiter (10/h) — lockout risk and lost per-user throttling.
- **Root cause:** two independent gaps. (1) No `app.set("trust proxy", ...)` anywhere, so Express ignored `X-Forwarded-For` and reported the proxy socket address as `req.ip`. (2) `chatLimiter` was mounted in app.ts *before* the router and therefore before `requireAuth`, so its key generator ran while `req.userId` was still unset — user-scoped keying was impossible regardless of the generator.
- **Fix applied:**
  - `TRUST_PROXY_HOPS` env (default 0 = direct, safe) reads an integer hop count; when > 0 the server calls `app.set("trust proxy", hops)` so `req.ip` is the XFF entry that many hops in. Documented in .env.example.
  - The cost-bearing `chatLimiter` is no longer mounted in app.ts. It is mounted inside the openai router immediately after `requireAuth`, path-scoped to the AI routes (`/openai/conversations`, `/openai/search`, `/openai/generate-image`) so the cheap `/openai/stats` read keeps only `statsLimiter`. Its `keyGenerator` now composes the signed-in user id with the client IP — `u<userId>:<ipKeyGenerator(req.ip)>` — falling back to IP alone. `ipKeyGenerator` (express-rate-limit v8) normalises IPv6 to /64 so clients cannot rotate within a subnet. Pre-auth limiters (`statsLimiter`, `authLimiter`, `registerLimiter`) stay IP-keyed deliberately (no user to key on; keying login failures on the target account would hand attackers a lockout lever).
- **Test added:** artifacts/api-server/test/rate-limit-keying.spec.ts (3 tests): (1) with `TRUST_PROXY_HOPS=1`, requests from distinct X-Forwarded-For addresses get independent buckets; (2) a second signed-in user sharing the proxy IP keeps their own bucket after the first exhausts theirs (this test fails with an IP-only key — verified by temporarily reverting the generator to `ipKeyGenerator(req.ip)`); (3) a single user still gets 429 after exceeding 30/min.
- **Verified by:** api-server suite 58 passed + 2 env-gated skipped; whole-workspace `pnpm test` 141 passed + 2 skipped; `pnpm typecheck` 0 errors; api-server production build green. Commit bcc3081.
- **Related:** Audit 3 F-02; session-cookie auth from BUG-003; Session 20.

### BUG-009 — Abandoned SSE streams never aborted
- **Severity / Status:** Medium / Fixed (2026-10-05, Session 20) — Audit 3 finding F-04.
- **Where:** artifacts/api-server/src/routes/openai/index.ts — POST /openai/conversations/:id/messages provider loop.
- **Symptom:** a client that disconnects mid-stream left the server consuming the provider stream (billable tokens) and writing to a dead socket until the model finished, and a partial assistant message was then persisted.
- **Root cause:** Node ≥16 fires IncomingMessage `close` as soon as the body is consumed — `express.json` does that before the handler runs — so `req.on("close")` never fires for a mid-stream disconnect in this app. The reliable signal is `res.on("close")` with `!res.writableEnded`.
- **Fix applied:** the route creates an AbortController; `res.on("close")` aborts it when the response hasn't ended; the signal is passed as the create *options* argument (`create(body, { signal })` — the OpenAI SDK v6 signature rejects `signal` in the body); the chunk loop breaks when aborted; the catch path returns silently once the client is gone; the assistant message is not persisted after an abort. A route comment documents the req-vs-res close distinction.
- **Test added:** artifacts/api-server/test/sse-abort.spec.ts (2 tests): a raw `http.request` client destroys its socket on the first response bytes; asserts the provider `create` call received an aborted AbortSignal, and that only the user-message insert happened (no assistant insert).
- **Verified by:** api-server suite 47 passed + 2 env-gated skipped; whole-workspace `pnpm test` 125 passed + 2 skipped; typecheck green. Commit 83104be.
- **Related:** Audit 3 F-04; BUG-002 (same handler, SSE error framing); Session 20.

### BUG-005 — DELETE conversations route validated a body-polluted params object
- **Severity / Status:** Medium / Fixed (2026-10-05, Session 18) — Audit 2 findings F-01 & F-05.
- **Where:** artifacts/api-server/src/routes/openai/index.ts — DELETE /openai/conversations/:id.
- **Symptom:** the handler ran `DeleteOpenaiConversationParams.safeParse(req.params)`; in Express 5, `req.params` is the merge of path params with parsed body/query fields, so a crafted request body could satisfy (or influence) a params-level schema. Body-parsing validation on a DELETE is a pointless attack surface: an attacker-controlled body should never participate in identifying the resource.
- **Root cause:** the orval-generated params schema (`zod.coerce.number()`) coerces anything, and zod's default object behavior strips unknown keys rather than rejecting them, so the schema added no protection while inviting body-polluted input.
- **Fix applied:** the route now takes only the path segment — `const id = Number(req.params.id)` — and rejects anything non-integer or non-positive with `400 {"error":"Missing or invalid conversation id."}`; no body parsing occurs. The unused `DeleteOpenaiConversationParams` import was removed (the generated schema remains in lib/api-zod for the response contract; it will return on the next orval codegen and must simply stay unused by this route). A missing id (trailing slash) matches no route under Express 5's `:id` semantics and yields the framework's 404. Covered by artifacts/api-server/test/delete-no-body-parsing.spec.ts (5 tests: body-ignored 204, non-numeric id 400, missing id 404, owned 204, other user's 404).
- **Verified by:** api-server suite 33 passed + 2 env-gated skipped; whole-workspace `pnpm test` 107 passed + 2 skipped; typecheck green. Commit c93fc6a.
- **Test-infra note:** Node's `http.request` only auto-frames POST/PATCH bodies with Transfer-Encoding: chunked; a length-less DELETE body is rejected by the HTTP parser (HPE_INVALID_METHOD) with a bare 400 before the app sees it. The shared test helper now sets Content-Length explicitly for any method carrying a body.
- **Related:** Audit 2 F-01/F-05; Session 18.

### BUG-004 — Conversations cursor pagination repeated the first page (gt vs lt on desc order)
