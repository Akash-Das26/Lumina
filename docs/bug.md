### BUG-021 — Wrong-provider key accepted by the startup check (no key-shape rule, no provider guidance)
- **Severity / Status:** Medium / **Fixed** (2026-10-17, Session 28).
- **Symptom:** every chat message showed "The AI service is not configured correctly. Please contact the administrator." Root cause confirmed by calling the provider directly: the configured key starts with `AQ.` (a Google-style key) while the app pointed at OpenAI, which expects `sk-`.
- **Root cause:** `readProviderConfig` only rejected *empty* values, *placeholder* shapes and a missing/malformed base URL — nothing tied the **key to the base URL**, so a perfectly-formed key from the wrong provider passed startup and failed at the first request as a generic auth error. Model names were hardcoded (`openai/gpt-oss-120b`, `gpt-image-1`) with no per-feature variables, there was no notion of feature capability, no standalone probe existed, and the provider-401 server log carried no host/prefix/model to diagnose the mismatch with.
- **Fix applied:**
  - **Key-shape check keyed to the base URL** (`lib/provider-config.ts`): when the base URL is the OpenAI default or unset, the key must start with `sk-` (excluding Anthropic's `sk-ant-`); a key that clearly belongs to another provider (`AIza`, `AQ.`, `gsk_`, `sk-ant-`, `xai-`) is refused with: `OPENAI_API_KEY does not look like an OpenAI key (expected it to start with "sk-"). If you are using another provider, set OPENAI_BASE_URL (or AI_INTEGRATIONS_OPENAI_BASE_URL) and the model variables for it. See README, "Choosing an AI provider".` — an unrecognised non-`sk-` key gets a same-purpose variant. Not one byte of the value appears in any message. With any non-OpenAI base URL the shape rule is skipped (only empty/placeholder/URL checks apply). Order is placeholder → shape → base URL presence/validity, so existing messages and tests are unchanged.
  - **Explicit provider choice:** `OPENAI_BASE_URL` accepted as an alias everywhere (both integration clients + config); per-feature model variables `OPENAI_CHAT_MODEL` (default `openai/gpt-oss-120b`) and `OPENAI_IMAGE_MODEL` (default `gpt-image-1`) — the chat route and the images client read them; no new dependencies.
  - **Capability honesty (images):** known-unsupported hosts (Google's OpenAI-compat endpoint) refuse Artist *before* a call with `501 {"error":"Image generation is not available with the current AI provider."}`, and a provider that answers 404/405/501 on the images call gets the same friendly copy at call time; every other failure keeps its normal mapping and the other tabs are untouched (asserted). The regenerate toast now shows the API's clean copy (`messageForFailure`) instead of an `HTTP 501 …` wrapper.
  - **Better 401/403 diagnostics:** `logProviderError` adds `providerHost`, `keyHint` (the fixed prefix class only, e.g. `key starts with sk-` — never the value), `model` (per failing route) and `hint: "See README → Troubleshooting local setup"` — server log only; the client copy is unchanged.
  - **`pnpm check:provider`** (new `scripts/check-provider.mjs`, root script): reads the same variables (env first, then `./.env` for unset ones), does one authenticated `GET {base}/models`, prints host/path + pass/fail + HTTP status (redacted snippet on failure), exits 0/1, never prints the key, never runs at startup or in CI. The stub provider gained `GET /models` (`STUB_MODELS_STATUS`) for its tests; `dev-local`'s early-exit hint mentions the command.
  - **Docs:** README gained **"Choosing an AI provider"** (variable table, tested-by-config OpenAI + Gemini examples, honest per-provider compatibility table with everything unverified marked *untested*, the `check:provider` first step) and a troubleshooting entry; `.env.example` documents both examples (placeholders only), the shape rule and the model variables.
- **Files changed:** `artifacts/api-server/src/lib/{provider-config,provider-errors}.ts`, `artifacts/api-server/src/routes/openai/index.ts`, `lib/integrations-openai-ai-server/src/{client.ts,image/client.ts}`, `artifacts/lumina/src/pages/chat-conversation.tsx`, `scripts/check-provider.mjs` (new), `scripts/browser/stub-provider.mjs`, `scripts/dev-local.mjs`, root `package.json`, `.env.example`, `README.md`, `docs/{bug,review,features}.md`.

### BUG-020 — Login brute-force limiter collapsed every account behind one IP into a single 10-attempt bucket (and the draft fix was dead code)
- **Severity / Status:** Medium / **Fixed** (2026-10-17, Session 27).
- **Where:** `artifacts/api-server/src/middleware/rate-limit.ts` (new `loginFailureKeyGenerator`, `authLimiter` wiring, corrected `registerLimiter` rationale, restored `userScopedKeyGenerator`), `artifacts/api-server/test/rate-limit.spec.ts` (+2 tests).
- **Symptom / impact:** `authLimiter` was created without a `keyGenerator`, so express-rate-limit's default keyed on the request IP. Behind one NAT/office proxy/captive portal — or any deployment with `TRUST_PROXY_HOPS > 0`, where every client behind the proxy legitimately shares one egress IP — **ten failed logins for any account locked out every account at that address for 15 minutes**, a trivial login DoS against a known colleague/tenant, and people sharing a network locked each other out by accident.
- **Dead draft found in the tree:** an uncommitted edit added an email branch inside `userScopedKeyGenerator` with comments claiming "failures are keyed by IP+email" — but that generator is only wired to `chatLimiter` (mounted after `requireAuth`, where `userId` is set and the body has no email), so the branch could never fire; `authLimiter` and `registerLimiter` still had no `keyGenerator`. It also introduced a fifth lint warning via `(req as any).body?.email`.
- **Fix applied:** new `loginFailureKeyGenerator` keys failed logins on **IP + trimmed/lowercased email** (the same normalization the login route applies, so case variants such as ` USER@TEST.DEV ` share one bucket) and is wired into `authLimiter` only; a missing/non-string email falls back to plain-IP keying (`express.json` runs in app.ts before the limiter mount, so the body is available). `registerLimiter` deliberately stays IP-keyed — including the submitted email would let one address create unlimited accounts just by varying the email — and its comment now says so. The dead branch was removed from `userScopedKeyGenerator` (no `any`, warning count back to 4). Security analysis: the composite key cannot lock a victim from a different IP (the attacker's IP is part of the bucket); same-IP lockout was already possible and strictly broader before this fix.
- **Tests added:** `rate-limit.spec.ts` +2 — (a) after `user@test.dev` exhausts its failed-login bucket, a different email from the same IP still reaches the credential check (401, not 429); (b) ` USER@TEST.DEV ` shares the exhausted bucket (429), proving normalization. Both fail against the pre-fix IP-only keying (a) and the un-normalized draft (b). Existing cases unchanged: the register test still uses 11 *different* emails to assert IP keying; successful logins still don't count.
- **Verified by:** whole-workspace `pnpm test` exit 0 — **321 passed + 4 env-gated skipped** (6 api-client-react + 166 api-server + 149 lumina); `pnpm typecheck` exit 0; `pnpm lint` exit 0 (0 errors, 4 known warnings — the draft's fifth is gone); `pnpm audit` clean.
- **Related:** BUG-007 (trust proxy + chat-limiter keying that made the topology question matter); Audit 4 A1 / Audit 5 F-01; Session 27.

### BUG-015 — An upstream 5xx was answered as a generic 500, and a proxy/gateway 5xx threw away the user's message
- **Severity / Status:** Medium / **Fixed** (2026-10-16, Session 24).
- **Where:** `artifacts/api-server/src/lib/provider-errors.ts`, `artifacts/lumina/src/lib/stream-message.ts` (`apiAnswered`, `errorReachedServer`, `ChatSendError.delivered`), `artifacts/lumina/src/pages/chat-conversation.tsx` (`failSend`), `artifacts/lumina/src/components/chat-input.tsx`, `artifacts/lumina/vite.config.ts` (proxy marker), tests `provider-errors.spec.ts` +1, `bug-014.spec.ts` +2, `test/stream-message.spec.ts` (new, 12), `test/chat-send-failure.spec.tsx` +1.
- **Symptom (two halves, one root: the failure was attributed to the wrong party):**
  - A provider answering 500/501/502/503/505 fell into the mapper's "anything else" class and became **500 "Internal server error"**, so a brief upstream outage read as a bug in this app, and the caller's Retry decision depended on a status that said nothing about the cause.
  - A 502/503 produced *in front of* the API (the Vite dev proxy when the API process is down, or any reverse proxy in front of it) was accepted by the client as "the API answered". The page then showed **Message failed to send** with Retry and dropped the optimistic bubble — but nothing had been persisted, so the typed text was simply gone and the user had to retype it. Reproduced through the dev proxy with the API stopped: the composer emptied on a 503.
- **Fix applied:**
  - `mapProviderError` now maps an upstream **5xx → 502 "The AI service is temporarily unavailable. Please try again."** while the real status, code and redacted message stay in the server log (`provider request failed`). Provider 408/504 remain in the 504 timeout class, where "did not respond" describes them.
  - The client stops trusting a 5xx by status alone: `apiAnswered(status, body)` treats only the API's JSON `{error}` contract as an answer, and the dev proxy marks its own response with `code: "api-unreachable"`. Anything else (HTML gateway page, non-JSON 5xx, marker) means the request never reached the app, so `ChatSendError.delivered` is false, the optimistic bubble is dropped, and `ChatInput` restores the typed text (`onSend` → `true`). One rule serves the SSE transport, the Search source lookup and API-client `ApiError`s alike.
- **Tests added/updated:** `test/stream-message.spec.ts` (new: mapped provider 5xx is *delivered* with the API copy; the proxy marker, a bare HTML 502 page and a rejected `fetch` are *not delivered*; a 4xx without a body still counts as answered; mid-stream error frames are delivered), `chat-send-failure.spec.tsx` +1 (proxy 502/503 keeps the composer text), `provider-errors.spec.ts` +1 (5xx → 502, real status still logged), `bug-014.spec.ts` +2 (route answers 502 with the mapped copy for an upstream 502/503).
- **Verified by:** whole-workspace `pnpm test` exit 0 — **316 passed + 4 env-gated skipped** (6 api-client-react + 164 api-server + 146 lumina); `pnpm typecheck` exit 0; `pnpm lint` exit 0 (see BUG-016). Real browser (`pnpm verify:flow`): both stub-provider failures still answered 502 with the mapped copy, Retry resends, no provider text in the page.
- **Limitations:** a proxy that returns a *JSON* body with an `error` string (without the dev proxy's marker) still counts as an API answer — the rule is deliberately conservative rather than guessing; the fix is aimed at the shapes the app itself can produce.
- **Related:** BUG-014 (this closes the status/copy gap it left), BUG-002 (SSE error framing).

### BUG-007 — Rate limiters keyed on proxy IP; no `trust proxy` handling
- **Severity / Status:** Medium / Fixed (2026-10-05, Session 20) — Audit 3 finding F-02; user-approved "env-tunable" option.
- **Where:** artifacts/api-server/src/app.ts (limiter mounting + `trust proxy`); artifacts/api-server/src/middleware/rate-limit.ts (key generator); artifacts/api-server/src/routes/openai/index.ts (limiter mount point); .env.example (`TRUST_PROXY_HOPS`).
- **Symptom:** behind the Vite dev proxy or any reverse proxy, `req.ip` was the proxy address, so every client shared one bucket for chatLimiter (30/min), authLimiter (10/15 min) and registerLimiter (10/h) — lockout risk and lost per-user throttling.
- **Root cause:** two independent gaps. (1) No `app.set("trust proxy", ...)` anywhere, so Express ignored `X-Forwarded-For` and reported the proxy socket address as `req.ip`. (2) `chatLimiter` was mounted in app.ts *before* the router and therefore before `requireAuth`, so its key generator ran while `req.userId` was still unset — user-scoped keying was impossible regardless of the generator.
- **Fix applied:**
  - `TRUST_PROXY_HOPS` env (default 0 = direct, safe) reads an integer hop count; when > 0 the server calls `app.set("trust proxy", hops)` so `req.ip` is the XFF entry that many hops in. Documented in .env.example.
  - The cost-bearing `chatLimiter` is no longer mounted in app.ts. It is mounted inside the openai router immediately after `requireAuth`, path-scoped to the AI routes (`/openai/conversations`, `/openai/search`, `/openai/generate-image`) so the cheap `/openai/stats` read keeps only `statsLimiter`. Its `keyGenerator` now composes the signed-in user id with the client IP — `u<userId>:<ipKeyGenerator(req.ip)>` — falling back to IP alone. `ipKeyGenerator` (express-rate-limit v8) normalises IPv6 to /64 so clients cannot rotate within a subnet. ### BUG-009 — Abandoned SSE streams never aborted
- **Severity / Status:** Medium / Fixed (2026-10-05, Session 20) — Audit 3 finding F-04.
- **Where:** artifacts/api-server/src/routes/openai/index.ts — POST /openai/conversations/:id/messages provider loop.
- **Symptom:** a client that disconnects mid-stream left the server consuming the provider stream (billable tokens) and writing to a dead socket until the model finished, and a partial assistant message was then persisted.
- **Root cause:** Node ≥16 fires IncomingMessage `close` as soon as the body is consumed — `express.json` does that before the handler runs — so `req.on("close")` never fires for a mid-stream disconnect in this app. The reliable signal is `res.on("close")` with `!res.writableEnded`.
- **Fix applied:** the route creates an AbortController; `res.on("close")` aborts it when the response hasn't ended; the signal is passed as the create *options* argument (`create(body, { signal })` — the OpenAI SDK v6 signature rejects `signal` in the body); the chunk loop breaks when aborted; the catch path returns silently once the client is gone; the assistant message is not persisted after an abort. A route comment documents the req-vs-res close distinction.
- **Test added:** artifacts/api-server/test/sse-abort.spec.ts (2 tests): a raw `http.request` client destroys its socket on the first response bytes; asserts the provider `create` call received an aborted AbortSignal, and that only the user-message insert happened (no assistant insert).
- **Verified by:** api-server suite 47 passed + 2 env-gated skipped; whole-workspace `pnpm test` 125 passed + 2 skipped; typecheck green. Commit 83104be.
- **Related:** Audit 3 F-04; BUG-002 (same handler, SSE error framing); Session 20.

### BUG-005 — DELETE conversations route validated a body-polluted params object
- **Severity / Status:** Medium / Fixed (2026-10-05, Session 18) — Audit 2 findings F-01 & F-05.
- **Where:** artifacts/api-server/src/routes/openai/index.ts — DELETE /openai/conversations/:id.
- **Symptom:** the handler ran `DeleteOpenaiConversationParams.safeParse(req.params)`; in Express 5, `req.params` is the merge of path params with parsed body/query fields, so a crafted request body could satisfy (or influence) a params-level schema. Body-parsing validation on a DELETE is a pointless attack surface: an attacker-controlled body should never participate in identifying the resource.
- **Root cause:** the orval-generated params schema (`zod.coerce.number()`) coerces anything, and zod's default object behavior strips unknown keys rather than rejecting them, so the schema added no protection while inviting body-polluted input.
- **Fix applied:** the route now takes only the path segment — `const id = Number(req.params.id)` — and rejects anything non-integer or non-positive with `400 {"error":"Missing or invalid conversation id."}`; no body parsing occurs. The unused `DeleteOpenaiConversationParams` import was removed (the generated schema remains in lib/api-zod for the response contract; it will return on the next orval codegen and must simply stay unused by this route). A missing id (trailing slash) matches no route under Express 5's `:id` semantics and yields the framework's 404. Covered by artifacts/api-server/test/delete-no-body-parsing.spec.ts (5 tests: body-ignored 204, non-numeric id 400, missing id 404, owned 204, other user's 404).
- **Verified by:** api-server suite 33 passed + 2 env-gated skipped; whole-workspace `pnpm test` 107 passed + 2 skipped; typecheck green. Commit c93fc6a.
- **Test-infra note:** Node's `http.request` only auto-frames POST/PATCH bodies with Transfer-Encoding: chunked; a length-less DELETE body is rejected by the HTTP parser (HPE_INVALID_METHOD) with a bare 400 before the app sees it. The shared test helper now sets Content-Length explicitly for any method carrying a body.
- **Related:** Audit 2 F-01/F-05; Session 18.

### BUG-004 — Conversations cursor pagination repeated the first page (gt vs lt on desc order)
- **Severity / Status:** Medium / Fixed (2026-10-02, Session 4)
- **Where:** artifacts/api-server/src/routes/openai/index.ts — GET /openai/conversations cursor filter.
- **Symptom:** with newest-first ordering (`orderBy(desc(id))`), page 2 requested with `cursor=3` returned ids 5,4 — the same rows as page 1 — instead of the older rows 2,1. Any paginated consumer would loop on page 1 forever.
- **Root cause:** the cursor filter used `gt(conversations.id, cursor)` while the sort is descending; the window `id > cursor` selects *newer* rows, which were already returned. The messages route (ascending + `gt`) was correct.

- **Fix applied:** filter changed to `lt(conversations.id, cursor)` with a comment explaining the desc/cursor relationship. Verified live: pages walk 5,4,3 → 2,1 → empty with no repeats. New integration suite artifacts/api-server/test/integration.pagination.spec.ts (env-gated on E2E_DATABASE_URL) asserts descending order, cross-page monotonicity and no repeated ids. Commit 67cfa86.
- **Verified by:** live curl against running dev server + integration tests (2 passed with real DB; skipped without).
- **Related:** BUG-003 (introduced by its pagination fix); Session 4.

### BUG-002 — SSE provider errors stream as mid-stream event instead of HTTP error status
- **Severity / Status:** Low / Fixed (2026-10-02, Session 2)
